# 会話エージェント・サイト設定・定期レポート

## 目的から評価根拠へつなぐ提案（Q3c-4c）

新規の改善提案には `evaluation.goal_checks` を1〜3件付ける。目的、出典と原文引用、必要な根拠、現在の確認状態、不足、次の確認、その確認が分析候補か担当者への確認かを分ける。出典は今回の依頼・サイト目標・ユーザーの作業記憶／確認済み合意で、原文の一致を検査する。AIの仮説を目的の出典に昇格しない。目的が未設定なら `goal_unconfirmed` とし、仮の目的と確認質問を示す。`proxy_only`／`unmeasured` も目的達成の判定ではない。

提案はWorkspaceとMarkdown回答に保存し、通常の再読込み・文書保存に残す。旧提案は項目なしで読める。提案作成時の `proposals_site_revision` を記録し、次ターンには `prior_goal_context` として未検証の確認事項を渡す。現在の設定revisionとの差や、このターンの根拠の有無を示す。設定変更・明示依頼を優先し、古い案を確定事実や長期合意として扱わない。

品質レビューは複数目的を個別に点検し、合格理由の引用が候補回答の評価説明に存在することを検証する。目的名の繰り返しだけでは評価の裏付けにしない。省略された目的は、元の認可済み文脈に実在する引用だけを限定修正へ渡す。この修正用の引用は診断ログ・例外文字列とは分離する。追加GA4取得はなく、次の確認も自動実行しない。

提案生成もモデルファミリーに対応した限定思考量を使い、提案60秒・回答55秒の既存期限内にレビューと最大1回の修正を収める。目的の意味的な網羅性はモデル評価であり、漏れや過剰差戻し、429・期限切れは残り得る。認可・read-only・DSS境界は従来の決定的な検査を維持し、サイト設定を禁止ポリシーへ変更しない。品質不合格時にも既存のFindingとグラフは保持する。

## 分析回答のMarkdown文書（2026-09-16）

エージェントの最終回答は`AnalysisMessage.content_format=markdown`として、Markdown原文を`content`へ保存する。見出し・箇条書き・ページごとの内訳表はBackendで構築し、LLMの文章・取得値はデータとしてエスケープする。数値計算・Evidence参照の検証は変更しない。末尾を省略する場合は段落の境界で止め、省略を明示する。

回答ごとに「プレビュー」「Markdown原文」「Markdownをコピー」「.md保存」を利用できる。コピー・保存はプレビューと同じ原文を使い、GA4取得やレポート作成を起動しない。Markdownファイルには本文・表・根拠IDが含まれ、EChartsの画像やDataset Blobは埋め込まない。ダウンロード後の文書には分析データが含まれるため、共有先に注意する。

旧履歴は`content_format=plain`が既定。元の本文は書き換えず、改行と既知の見出し・箇条書きを表示時だけ整形する。ログイン・DSS認可・履歴アクセスは既存経路を使う。プレビュー切替や出力のために別のブラウザ永続キャッシュは作らない。

Frontendは固定版MarkedのLexerで構文木を解析し、Svelteのテキスト補間と許可したタグだけで描画する。`{@html}`は使用しない。HTMLは文字として表示し、画像・iframe・スクリプトは実行／読込みしない。リンクはユーザー操作によるHTTP(S)のみとし、相対URL・危険なscheme・資格情報付きURLを拒否する。表はキーボードで横スクロール可能にする。参照: [MarkedのLexer・Token仕様](https://marked.js.org/using_pro#lexer)。

通常の回答の整形・Markdown保存は、ユーザーが明示して初めて作成するレポートとは別機能である。

## 短い絞込み指示の条件保持（Q3a）

既に通常GA4分析を行った会話で「Organicだけ」「その中でモバイルだけ」等を送ると、登録済みFilterを変更し、指標・集計軸・対象期間・比較期間・粒度を保つ契約を適用します。AIが別の指標や軸に変える計画を返した場合は取得前に拒否し、既存予算内で再計画します。修復できない場合は不足と理由を返し、誤った条件を完了扱いにしません。

この保証は短い肯定の登録Filter指示が対象です。期間・指標・軸の明示変更、否定・相談・追加取得禁止を含む文は、通常の計画・検証へ渡します。任意の自然言語を網羅する仕組みではなく、ランキング件数や要約統計の完全な継承は別課題です。[Q3a検証](evaluation/q3a-filter-continuation-2026-09-25.md)

## 明示的な条件変更（Q3b）

「比較基準だけ2026年4月に変更してください」「月別から日別に変更してください」「参照元からランディングページに変更してください」など、現在の条件に対する短い単一変更を別契約として扱います。変更指定のない期間・指標・軸・Filterは保持し、旧軸の取得を要求し続けたり、日付以外の軸を落としたりしないよう実行前と完了時に検査します。「比較だけ解除して」も条件未指定と区別します。

登録済みで曖昧さのない語を使う限定契約です。複合指示、任意文言、相対的な比較基準、追加取得禁止等をこの契約に押し込みません。実Geminiで同じ限定シナリオを2回確認し取得計画12/12が一致しましたが、一般的な理解率や文章品質の検証ではありません。[Q3b検証](evaluation/q3b-condition-change-2026-09-25.md) / [実Gemini検証](evaluation/q3-live-planning-2026-09-25.md)

## 作業記憶・過去検索・段階計画

会話右側に「会話の作業記憶」と段階分析の進捗が表示されます。目的・ユーザー方針・対象ページ・未検証仮説・確認事項を分け、会話本文が直近範囲から外れても計画へ渡します。不要なユーザー項目は「作業記憶から外す」で除けます。数値はこのメモから信用せず、Finding／Evidenceで検証します。

長期的に使う制約は、設定画面で対象を選び「記憶と過去の分析」から候補を追加→内容を確認して確定してください。「覚えて」と会話で依頼した内容も未確認候補です。訂正は再確認待ちへ戻り、削除は次の会話から長期記憶として参照しません。元の会話や過去の回答は残ります。

同じ設定画面で「2026年5月 /campaign/ 参照元」等を検索できます。自分の同じData Source Setの分析だけが対象です。新規結果と、会話再開時の旧Workspace内の結果が検索されます。検索は最大500候補・8結果の語句一致で、全件・意味検索ではありません。

例: 「2026年5月のPV上位10ページを確定し、各ページの参照元を調べ、違いと改善案をまとめて」

先にページ単独の上位を確定し、そのページごとに参照元上位5件を調べます。単純なページ×参照元の全体上位10組合せとは異なります。選定1回＋対象数の取得を同じ依頼内で自動実行します（5対象なら6分析、10対象なら11分析）。実行中に「続き」を送る必要はありません。対象・親条件・進捗・根拠は保存します。対応範囲は登録カテゴリ2軸・1指標・単一期間・最大10対象で、期間比較や任意の多段調査を全部実装したものではありません。

「新しいデータ取得はせず、前回の結果を説明してください」は追加取得禁止としてコード側で扱い、PlannerやGA4を呼ばずに再認可済みの根拠だけを文章化します。途中の結果しかなければ不足を明示し、勝手に取得を補いません。文章化は取得済みラベル中の数字（例: URLの年）と計測値を区別し、未観測URL・自由な数値計算は禁止したままです。

詳細: [ADR 0012](adr/0012-conversation-memory-and-dependent-analysis.md)。

## 複数軸の分析（2026-09-14）

「2026年5月のページと参照元を掛け合わせたPVを分析」「チャネル×デバイス×ページをPVでクロス集計」「月別とチャネルを掛け合わせてUUを確認」などを、登録済み2〜4軸の組合せとして扱います。GA4互換性検査に通る組合せだけ実行します。

単一期間でも組合せごとの数値を根拠に残し、回答へ渡します。表は全軸を表示します。組合せの上位とページ全体の上位は同じではなく、サンプルのUUを足し合わせても全体UUにはなりません。グループ別の段階分析は上記の別契約で扱い、raw journeyや全件網羅までは保証しません。

検証: 保存済みの該当実結果から10組合せを再認可して復元できました。実Gemini＋合成応答でも上記3種類の計画・取得・根拠付き回答が完走しています。実GA4各組合せの互換性や管理画面との数値突合とは区別しています。

## Geminiの生成設定・一時障害（2026-09-18）

Gemini 3系はtemperature 1.0、行動選択・型付き引数生成・根拠の文章化はthinking level LOWを使用します。改善相談はモデル既定の思考設定を維持し、2.5系の既存budgetとは混ぜません。計画や数値を正しいものとして受け入れる条件は変えず、型・認可・Evidenceをコードで検証します。

HTTP 429はGemini側の利用量／容量制限としてGA4 quotaと区別します。4〜6秒のジッター付き待機で1回だけ再試行し、同じ処理期限内に収めます。上限後はpartialを返し、取得済み結果を保持します。Token・プロンプト・生成本文をログに出さず、phase・HTTPコード・試行番号・所要時間を記録します。モデル変更・追加課金枠・期限延長は自動では行いません。

実GA4の日別→月別→日別と途中429からの回復を確認しましたが、恒久的な外部障害の解消や無条件の完走を保証するものではありません。[Q2b-1完了記録と公式参照](evaluation/q2b-1-completion-2026-09-18.md)。

## 使い方

### 改善仮説の評価方法（Q3c-2、2026-09-26）

新しい改善提案には、サイト目的との関係、指標の選択理由、計測の限界、実施前の確認事項を付けます。登録済みの指標でも事業成果そのものとは限らず、適切な指標が未確定の場合は未確定のまま説明します。サイト設定で分析や提案を禁止する仕組みではありません。

提案を文章化の入力にも渡し、評価方法はモデルが省略しても回答のMarkdownへコード側で保持します。右パネル・履歴・明示作成したレポートから確認できます。旧形式の提案・過去の回答は自動で書き換えません。参照元だけで媒体や会員属性を断定せず、ページ×参照元集計を遷移・クリックの実測として扱わないよう生成を補助します。認可や追加取得禁止は従来どおりです。[実測と限界](evaluation/q3c-2-measurement-reasoning-2026-09-26.md)

### 設定と相談

Q3c-4a（2026-09-26）: 改善提案の評価指標候補は、そのターンの登録済みMetric名または未確定に限定します。モデルがGA4物理名やAliasを返した場合は、提案生成の同じ期限内で1回だけ修復します。根拠の検査は維持し、曖昧な物理名の自動変換や追加のGA4取得は行いません。旧提案の保存形式は変えません。[検証記録](evaluation/q3c-4a-canonical-metrics-2026-09-26.md)

サイドバーの「サイト設定・定期レポート」を開きます。

1. 分析対象を選び、サイト基本情報・対象者・事業ゴール・技術／運営背景・コンテンツの方向性を保存します。AIがサイトを理解するための参考情報で、禁止事項やアクセス権の設定ではありません。
2. 関心のある改善領域、新規コンテンツ／リライト案への関心をチェックします。OFFや未選択でも分析・相談を拒否しません。未入力でも分析でき、会話の明示依頼を優先します。保存キーは互換のため旧名を維持しています。[ADR 0013](adr/0013-site-understanding-not-policy.md)
3. 不要なPropertyを非表示にします。個人の選択一覧だけに反映され、権限や定期実行は変わりません。
4. 分析画面で「追加調査・レポート・施策相談」をONにして質問します。OFFでは従来の単発分析です。

例:

```text
先月の集客と回遊を調べて。主要KPI、チャネル、上位ページを順番に確認してレポートにして。
そのページをOrganicに絞って深掘りして。
モバイルの絞り込みは解除してサイト全体で見て。
広告費は増やせません。記事から関連ページへの導線改善に絞って提案して。
最初の案について、見出しと説明文、検証方法を具体化したい。
```

不足情報は質問、必要な場合だけGA4を追加取得します。調査ごとのグラフは既存のMessage履歴へ保存されます。レポートには目的・調査section・根拠・改善仮説・未解決事項が残り、Markdownで保存できます。「この施策を詰める」ボタンから相談を続けられます。

レポートは「レポートを作成して」等の明示指示がある場合だけ表示・出力します。単に分析を依頼した場合は会話で回答します。「レポートは不要」で解除できます。有効化済みの定期レポートは作成指示として扱います。内部調査はユーザー発言ではなく「AIが実行した調査」と表示します。

画面右側のパネルにレポート・改善提案を表示します（狭い画面では会話の下）。GA4接続とProperty選択はヘッダーの「GA4接続・プロパティ」からモーダルを開きます。分析条件・状態と根拠データも、会話ヘッダーの各ボタンからモーダルで開きます。閉じるボタンまたはEscapeで会話へ戻れます。

設定は**個人×Data Source Set**単位です。他ユーザーとの共有設定ではありません。更新は次の会話から反映されます。Reportには使用した設定revisionを残します（過去設定本文のversion archiveは未実装）。最大24調査section、20会話要約を直近コンテキストに保持します。古いChat／Findingは既存履歴側に残ります。

### 同一セッションでの条件継承と計画期限

2026-09-14検証: Backend 333件、mypy 73ファイル、Ruff成功。実Gemini＋合成GA4で「参照元比較→LP深掘り→mobile→結果の説明」が同一セッションで完走し、最後の説明はGA4追加取得なしでした。実GA4の数値突合とは別の検証です。

「参照元別の比較」→「ランディングページを深掘り」→「その中でモバイルだけ」のような続きでは、省略したMetric・期間・比較期間・Filterを型付きAnalysis Stateから引き継ぎます。Metricの省略はGA4引数Schemaの検証前に解決し、その後CompilerがSemantic scopeを再検証します。初回のMetricや未定義CVを勝手に作ることはありません。

保存履歴を丸ごと計画へ渡すのではなく、今回の質問全文、直近4発言（各最大1,000文字）、確認質問、構造化条件、認可済み最大8sectionを渡します。GA4引数を生成する段階には施策案・数値Fact全文・過去の実行traceを渡しません。観測値は正確な値を保持し、文章を切り詰めたものからFilterを作りません。履歴保存自体は削減しません。

「今のランディングページの結果を説明してください」のような明示的な既存結果の解説は、同じ期間・比較期間・Filterと再認可済みFindingを持つsectionで回答できます。条件変更や曖昧な指示はこの近道を使わず、通常の計画・Cache検証を通ります。登録済みの明示的な「モバイルだけ」等の絞込みについては、合致する観測結果がないまま完了としません。自動の多角的レビューでは主分析の条件を保存し、最後の補助調査がページ別だったことを理由に次の質問をページ別へ固定しません。各補助結果のグラフ・根拠はそのまま履歴に残ります。

計画を全段階まとめて45秒で止める方式は廃止しました。行動選択30秒、GA4引数生成60秒、改善提案生成60秒のそれぞれにdeadlineを持たせ、形式エラーは失敗した段階だけを1回修復します。再生成・一時障害retryも同じdeadlineに含み、検証済みの行動選択をやり直しません。SDKの暗黙retryは無効化し、一時障害だけアプリで1回再試行します。調査240秒／会話全体300秒は費用・占有・キャンセルを制御する安全上限として残します。段階のtimeoutはGA4 quotaや調査全体のtimeoutと区別して表示し、取得済み根拠の回答を試みます。上限をなくして無期限に実行する設計ではありません。

## 多角的な期間評価

### 行動選択とGA4 Toolの分離（2026-09-13）

通常の会話経路は、まず小さいSchemaで目的・Workflow Skill・次の行動・残る調査を選びます。行動は`ga4.analyze`、`user.ask`、`evidence.answer`だけです。GA4を選んだ場合だけ別SchemaでSemantic引数を作り、既存Compiler→認可Gatewayへ渡します。質問や取得済み根拠からの回答のためにGA4を必ず呼ぶ構成ではありません。施策提案のSchemaもGA4引数生成から分離しています。

上位Skillは`analysis.exploration.v1`、`analysis.acquisition_comparison.v1`、`advisory.site_improvement.v1`です。GA4側のKPI／比較／深掘り等のSkillは下位の実行契約として再利用します。2026-09-13の追加改修では、明示された登録済みMetric／Dimensionと対称な2暦月比較の達成判定を**全Workflow共通**にしました。対応する今回のEvidence・観測値・期間の取得がなければ、1回再計画させ、その後も未確認ならpartial回答として不足を明記します。Workflow名を変更して完了判定を回避することはできません。すべての業務目的・複合条件まで機械検査済みという意味ではありません。詳しくは[ADR 0011](adr/0011-agent-tool-and-workflow-contracts.md)を参照してください。

### 共通分析Capabilityとカテゴリ比較

`agent/capabilities.py`は集客、ページ、属性・地域、技術環境、イベント・利用状況、時系列の観点と、登録済みの集計軸・前提・未対応機能をAgentへ渡します。SemanticはGlobal→Company→Data Source Setの実行時と同じ優先順位で解決し、下位で利用不可にした定義・Aliasを上位Catalogから再公開しません。Capabilityは権限や互換性の保証ではなく、各呼出しには従来のCompiler、OAuth、Gateway、Core互換性検査が必要です。

カテゴリ比較は、参照元だけでなくページ・地域・端末・イベント等に共通のコードで、全Dimensionの組合せが同じ行を照合します。対象値・比較値・差分・増減率を`Finding.category_comparisons`へ最大20件保存し、Agentへ渡します。未取得、明示ゼロ、重複行による曖昧さを区別し、UUや率を足し合わせません。回答には取得範囲内の内訳を最大4指標×10件表示するため、文章生成に失敗しても代表KPIだけの回答に戻りません。全体寄与や因果関係はこの比較だけでは判断できません。

Realtimeは専用Schema、Funnelは承認済みステップ定義を必要とします。Funnel専用入力には通常のMetricを必須にしません。未登録のファネル／custom項目、未実装のcohort／pivot、保留中のBigQuery経路は対応済みと表現しないよう明示します。

「2026年5月と2026年6月を比較した流入元の分析」では、6月1〜30日を対象、5月1〜31日を比較基準とし、比較方向と日数差を回答に表示します。指標未指定なら登録済みセッション数とアクティブユーザー数を候補とし、採用した仮定を明記します。CVは勝手に作りません。任意の2期間も型付きで保持できます。方向指定・日付指定・会計期間は単純な2暦月抽出では補完せず、Plannerで解釈します。

各GA4実行の条件・成否・EvidenceはWorkspaceの`execution_steps`、次の課題は`remaining_tasks`へ保存します。これは最新turnのtraceであり、完全なOperation ledgerではありません。明示的な分析軸を固定4観点へ置換せず、通常経路では取得後に再びAgentが判断します。以下の明示半期レビューのみ、既存の限定agenda経路が残っています。

Planner SDK失敗でも、可能なら取得済み根拠からpartial回答を生成します。Providerの429／一部5xxだけを既存時間予算内で1回再試行し、400／403や認可失敗は再試行しません。ログにはエラー型・安全なHTTP status・request IDを残し、SDK例外本文やTokenは記録しません。画面は手動停止、通信断、サーバーエラー、時間上限を区別し、異常終了時に履歴を一度だけ読み直します。分析の自動再実行はしません。

### 限定的な半期レビュー経路

「2026年上期のpage viewとアクティブユーザーについて多角的に分析して上期の評価をしてください」のような依頼では、最初のIntentPlanの期間・指標・比較条件・分析フィルタを基に、最大4観点のレビューを進めます。

年と上期／下期と登録指標が明示され、特別なフィルタ等がない依頼は、初回のLLMによる空計画を避けるためコードで初期IntentPlanを組み立てます。この限定経路は暦年上期を1〜6月、下期を7〜12月とし、比較指定がなければ前年同期を基準とします。仮定は回答に明示します。年度・会計年度や個別の比較／フィルタ指定はこの限定経路では解釈せず、通常の会話Plannerへ渡します。

1. 期間全体のKPI（アクティブユーザーは期間全体の重複排除値）
2. 期間内推移（63日以上では月次。それ以外は日次）
3. 流入チャネル別の上位分析
4. 主要ページ別の上位分析

登録済みSemanticで利用できる観点だけを候補とし、チャネル／ページがなければデバイスを候補にします。初版では1〜3指標の「多角・多面的・包括的・網羅的・総合分析／評価」が対象です。それ以外は従来の観測→次の判断のループを利用します。追加の明示的な観測値フィルタを伴う深掘りも従来経路です。4観点で全GA4分析を網羅するものではありません。

各観点は従来のSemantic Compilerと認可Gatewayを必ず通ります。未取得の観点は完了扱いにせず、最終回答に不足を残します。上位カテゴリ分析は比較期間を含めた返却件数制限があるため、同じカテゴリの比較値を取得できない場合があります。欠落はゼロではありません。寄与度は両期間に取得できたカテゴリ内の増減に対する割合であり、全サイトの増減寄与とは区別します。

最終評価は計画用の大きなSchemaから分離した専用Schemaを使います。コード計算済みの比較値・順位・寄与度、観点別の期間／フィルタ、品質注意事項を渡し、解釈ごとにFinding IDを検証します。回答の数値・Evidenceはコードで差し込み、増減率は表示だけ小数2桁へ丸めます（保存値の精度は維持）。年月を含む計画の説明だけで有効なqueryを捨てません。最終説明での自由な数値生成は引き続き拒否し、検証に失敗するとフィールド位置を返して一度だけ再生成します。GA4という製品名は数値主張と区別します。

意図文を言い換えただけの同じ実行引数は重複として拒否します。実行前のSemantic／形状検証失敗は取得回数を消費せず、計画回数内で修正します。内部調査ごとの重複したLLM文章化を省き、最終の横断評価に時間を残します。要約自体が失敗しても、コードで確認済みの期間KPIの方向性・根拠・未確認の観点・次の調査を回答します。事業目標の達成や因果関係は勝手に断定しません。

## 定期レポートの実行

設定画面で対象、質問、週次／月次、曜日／日（1〜28日）、時刻、IANAタイムゾーンを登録し、有効化します。週次は直前に完了した月〜日、月次は直前の暦月を対象にします。質問に別期間が書かれていても定期レポートではこの期間が優先されます。過去の完了結果はSession履歴に追加されます。

本番はCloud Schedulerの5分dispatch、ローカルは60秒pollです。指定時刻ぴったりの開始を保証しません。長期停止後に全回を遡って実行せず、最初の未処理回を1回実行して次の未来時刻へ進めます。夏時間の存在しない時刻はskipし、二重になる時刻は1回のみとします。

途中で質問が必要になった場合は、確認事項を含むReportを残します。実行状態は設定画面に表示します。メール・Slack通知は未実装です。非表示と定期停止は別操作です。一時停止は今後の実行を止めますが、開始済みのレポートは完了する場合があります。

## ローカル起動

Firebase／GA4 OAuth／Vertexとdev Firestoreが利用できる既存`.env`が前提です。CredentialはBackendだけに渡します。

今回はCloud Storageを新規作成せず、`compose.scheduler.yaml`がAPIとWorkerに共通の`dataset-cache` named volumeをマウントします。metadataは既存Firestore、結果blobはこのvolumeへ保存します。`cache-init`はvolumeディレクトリの所有者・0700 permissionを設定して正常終了する一度限りの初期化サービスです。

```bash
docker compose -f compose.yaml -f compose.firestore.yaml -f compose.scheduler.yaml up --build -d
docker compose -f compose.yaml -f compose.firestore.yaml -f compose.scheduler.yaml logs --tail=30 report-worker
```

Worker停止:

```bash
docker compose -f compose.yaml -f compose.firestore.yaml -f compose.scheduler.yaml stop report-worker
```

Workerを使わず画面と会話だけを確認する場合は従来の2つのCompose fileで起動できます。スケジュールの登録だけではWorkerは起動しません。`ANALYTICS_AI_ENABLE_ANALYTICS_TOOLS=false`時は会話実行とschedule有効化を拒否します。WorkerはFirestore必須です。

**今回の永続履歴を継続利用する際は3つのCompose fileを指定してください。** 従来の2file構成は`.env`次第でmemory cacheへ戻るため、共有volume内のグラフを復元できません。メモリキャッシュのままでのschedule有効化とWorker起動は拒否します。

通常の再起動・`docker compose down`ではvolumeは残ります。`down -v`／volume削除は結果データを失うので実行しないでください。PC・Dockerが停止中は定期実行できません。ブラウザを閉じてもPC上のDockerが動いていれば実行できます。ローカルvolumeの暗号化・バックアップ・容量監視はホスト側の責任です。TTLは再利用期限でありファイル自動削除ではないため、長期利用時のretention運用は別途必要です。従来のmemory cacheにしかなかったグラフは、この変更では復元できません。
